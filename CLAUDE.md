# PLAYR — контекст проекта

Персональный музыкальный плеер внутри Telegram (Mini App + бот). Пользователь шлёт свои треки боту, слушает их в Mini App. Никакого внешнего каталога и поиска чужой музыки.

## Статус
- `index.html` — тестовый Mini App (один файл, без сборки), текущая сборка **ios-7** (константа `BUILD` + видимая метка под треком; при каждом изменении увеличивать). Хостинг: GitHub Pages, подключён к боту через BotFather → Menu Button. Для сброса кэша Telegram в ссылке используется `?v=N`.
- Тестовое устройство: iPhone, iOS 26.4, Telegram iOS, Bot API 9.6. WebView отдаёт в UA `iPhone OS 18_7` — заморозка UA, не реальная версия.
- **Работает на iOS**: фон (свёрнутый Mini App, другой чат, рабочий стол, блокировка), автопереход между треками, ⏮ ⏭ на экране блокировки и в шторке, перемотка ползунком на экране блокировки, обложка/название, кнопки наушников, стриминг по сети в фоне.

## Открытые проблемы iOS
1. **Голосовое сообщение в Telegram ломает воспроизведение.** Системная пауза → через ~6 с iOS сама шлёт `play` → элемент застревает в `waiting`: `paused === false`, время не идёт, звука нет, UI показывает «играет». Пересоздание `<audio>` на той же позиции (`hardRestart`) не помогает. Гипотеза: WKWebView живёт в процессе Telegram и делит с ним AVAudioSession; нативный плеер голосовых деактивирует сессию, а веб-код не может её активировать без жеста пользователя.
   **ios-6 (проверено):** детектор зависания работает — после голосового кнопка в PLAYR и на экране блокировки показывает ▶. **Нажатие ▶ в PLAYR возвращает звук** (шаг 1: Web Audio `suspended → running` + `play()`). Нажатие ▶ на экране блокировки звук НЕ вернуло; в логе (последние 80 строк) не видно, доходил ли `MS: play`. Сама музыка после голосового не продолжается.
   **ios-7 (ждёт проверки):** (а) Web Audio заводится в жесте уже при первом ▶, пишутся его `statechange` — смотрим, возобновляет ли его iOS после голосового; (б) при зависании сначала авто-попытка без нажатия (`actx.resume()` + pause/play), не помогло — пауза; (в) при паузе из-за зависания карточка экрана блокировки (metadata, обработчики, `playbackState`) отправляется заново — гипотеза: после голосового карточку занимает нативный плеер Telegram и ▶ на экране блокировки уходит ему; (г) в отчёте 150 строк лога. Ключевой вопрос: есть ли в логе `MS: play` после нажатия ▶ на экране блокировки. Если нет — команда до веб-страницы не доходит, и для MVP остаётся «вернуться в PLAYR и нажать ▶».
2. **Шторка (Пункт управления): после мелкой перемотки ползунок остаётся на старом месте**, хотя звук перематывается (ios-6: `seekto` приходят и применяются точно, ползунок в шторке сам движется). Гипотеза: WebKit/iOS не считают малый сдвиг позиции изменением и карточку не обновляют. ios-7: режим F — после перемотки `setPositionState` с длительностью +0,01 с, на `seeked` — с настоящей (два «новых» состояния подряд); режим G — F + повторная отправка metadata. Если не поможет ни то, ни другое — принять как ограничение iOS. Низкий приоритет, на экране блокировки работает.

## Решения, которые уже приняты
- **Media Session на iOS (режим A)**: обработчики `play`, `pause`, `stop`, `previoustrack`, `nexttrack`, `seekto`; `seekbackward`/`seekforward` = `null`. **Перерегистрировать обработчики на каждом событии `play`** — иначе iOS показывает ±10 с вместо ⏮ ⏭ (WebKit подхватывает команды только при активной аудиосессии).
- `setPositionState`: после `seekto` сразу передавать целевую позицию, на паузе `playbackRate: 0`, подтверждать на `seeked`.
- Аудио не транскодировать в Opus (плохая поддержка в Safari/iOS). Хранить MP3/AAC как есть.
- `play()` — глушить `AbortError` (возникает при быстром переключении трека).
- Ссылки на файлы Telegram (`getFile`) содержат токен бота — клиенту не отдавать, только через прокси бэкенда или собственное хранилище.
- Шеринг в чужие чаты — через inline-режим (`InlineQueryResultCachedAudio`) или `savePreparedInlineMessage` + `WebApp.shareMessage()`, не через `sendAudio`.
- Deep links: `t.me/<bot>/<app>?startapp=<param>`, читать `start_param`.
- initData валидировать на сервере HMAC-SHA256 (ключ от `"WebAppData"` + bot token).

## Не проверено
- Звонок (проверялось только голосовое).
- Длительный фон (30–60 мин на заблокированном экране, сетевые треки) — риск выгрузки WebView по памяти.
- Android (энергосбережение Xiaomi/Samsung/Huawei), Desktop.

## MVP (следующий этап)
1. Бот: приём аудио, в т.ч. массовая пересылка из «Избранного»/каналов; ответ с кнопкой открытия Mini App.
2. Бэкенд: библиотека треков, метаданные ID3, стриминг с поддержкой HTTP Range.
3. Mini App: библиотека, поиск, мини-плеер + полный плеер, избранное.
4. Монетизация с первого дня: бесплатная квота на треки/объём, Premium через Telegram Stars.
5. Альбомы/артисты — через GROUP BY по полям трека, без отдельных таблиц.

## Право (РФ)
- БД с данными граждан РФ — на серверах в РФ (152-ФЗ, ч. 5 ст. 18), уведомление РКН как оператора ПД.
- Позиция сервиса — информационный посредник (ст. 1253.1 ГК РФ): оферта + notice & takedown, быстрое удаление по жалобе. Учитывать ст. 15.2 149-ФЗ.
- Никаких публичных плейлистов/каталога чужой музыки в MVP.

## Рабочий процесс
- Отвечать по-русски, кратко и по делу.
- После каждого изменения `index.html`: поднять `BUILD`, закоммитить и запушить в `main`, напомнить поменять `?v=N` в BotFather.
- Отчёты с устройства пользователь присылает текстом (кнопка «Скопировать отчёт»): разбирать по логу, а не только по вердиктам.
